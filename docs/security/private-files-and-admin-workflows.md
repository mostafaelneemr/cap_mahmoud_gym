# أمان الملفات الخاصة وتدقيق سير العمل الإداري غير المكتمل
(Task 8 — Private File Security & Incomplete Admin Workflow Audit)

## 1. الملخص التنفيذي
تم في هذه المهمة تدقيق وتأمين وصول الملفات الحساسة (وبالأخص صور تطور المتدربين `trainee_progress_photos`)، بالإضافة إلى التحقيق في استدعاء التنقيح المعلق `dd($id, $request)` داخل `SettingController::updateActivateSection` ومعالجته بأمان تام وفق قواعد العمل وبنية الصلاحيات في التطبيق.

جرى التأكد من الحفاظ على كامل التعديلات والملفات المنشأة في المهام السابقة (1 إلى 7)، والعمل بشكل حصري على الفرع `refactor-project` مع الالتزام الصارم بقواعد الأمان الإنتاجي (عدم لمس قواعد البيانات الحقيقية، والاعتماد الحصري على SQLite في الذاكرة أثناء تشغيل الاختبارات).

## 2. معمارية تخزين الملفات وتصنيفها (File Storage Architecture)

### أ. الملفات العامة (Public Assets)
* **المسار الفعلي:** `public/upload/...` و `storage/app/public/...` (عبر الرابط الرمزي `public/storage`).
* **الاستخدام:**
  - شعار الموقع وإعدادات الواجهة (`upload/setting`).
  - صور المقالات والمدونة والصفحات العامة في إدارة المحتوى (`upload/posts`).
  - صور الآلات والتمارين العامة (`upload/exercises` أو المرفقات التوضيحية للتمارين).
* **حالة الأمان:** تظل هذه الملفات عامة ومتاحة لزوار الموقع ومحركات البحث كما صُممت، دون أي تعديل على سلوك التخزين العام لها.

### ب. الملفات الحساسة الخاصة (Private & Sensitive Assets)
* **النوع الأساسي:** صور المتابعة الأسبوعية وقياسات التطور البدني للمتدربين (`TraineeProgressPhoto`).
* **طبيعة البيانات:** صور شخصية حساسة للمتدربين تظهر قياسات وتطورات أجسادهم لا يجوز الاطلاع عليها إلا من قبل المتدرب نفسه ومدربه المشرف والإدارة.
* **الوضع السابق:** كانت تُحفظ داخل القرص العام `Storage::disk('public')` في المجلد `progress_photos/`، ويتم عرضها بروابط عامة مباشرة عبر `asset('storage/' . $photo->photo_path)`.
* **الحل المطبق في هذه المهمة:**
  1. إنشاء نقطة وصول ويب محمية بالصلاحيات وجلسات المصادقة: `GET /system/trainee-progress/photo/{photoId}` (`system.trainee-progress.photo`).
  2. إنشاء نقطة وصول API محمية برمز Sanctum: `GET /api/v1/trainee/photos/{photoId}` (`api.trainee.photos.serve`).
  3. تحديث ملحق الرابط `photo_url` و `secure_url` في نموذج `TraineeProgressPhoto` ليعيد الرابط المحمي تلقائياً.
  4. التحقق الخادمي الصارم من هوية المستخدم وملكيته للسجل قبل تخديم الملف.
  5. فحص مسار الملف وحمايته من هجمات تخطي المسار (Path Traversal) والتحقق من نوع MIME للملف.
  6. إضافة ترويسات أمان تمنع التخزين المؤقت الوسيط للملفات الحساسة: `Cache-Control: private, no-cache, no-store, must-revalidate`.

## 3. قواعد التحقق والصلاحيات لصور التطور (Authorization Rules)

| نوع المستخدم | الصلاحية وقاعدة التحقق الخادمية | الاستجابة عند انتهاك القاعدة |
| :--- | :--- | :--- |
| **زائر غير مسجل (Guest)** | رفض فوري؛ لا يمكن استعراض أي صورة بدون جلسة مصادقة سارية. | إعادة توجيه لصفحة تسجيل الدخول `302` أو خطأ `401 Unauthorized` |
| **متدرب (Trainee - user_type 2 أو 3)** | يُسمح له فقط باستعراض الصور التابعة لسجلاته الشخصية (`$photo->checkin->trainee->user_id === $authUser->id`). | رفض فوري برمز `403 Forbidden` عند محاولة طلب معرف صورة متدرب آخر |
| **المدرب المعتمد / المشرف (Coach/Admin)** | يُسمح لهم باستعراض صور المتدربين للمتابعة وتقديم الملاحظات الرياضية. | `200 OK` مع بث محتوى الصورة بترويسات خاصة |
| **معرف غير موجود أو تالف** | التحقق من وجود السجل في قاعدة البيانات ومطابقته لرقم معرف صالح. | `404 Not Found` |

## 4. الحماية من هجمات المسار والتلاعب بالملفات (Path Traversal & Integrity)
1. **عدم الوثوق بمدخلات المسار:** يتم جلب مسار الملف حصرياً من سجل قاعدة البيانات المعتمد، ولا يُسمح للمستخدم بتمرير مسار ملف من عنده.
2. **فحص الرموز الخبيثة:** رفض أي مسار يحتوي على تسلق المجلدات `..` أو البايت الصفري `\0` أو بروتوكولات خارجية `://`.
3. **التحقق من الجذر التخزيني (Storage Root Boundary Check):**
   ```php
   $disk = Storage::disk('public');
   $realDiskRoot = realpath($disk->path(''));
   $realFilePath = realpath($fullPath);

   if ($realFilePath === false || !str_starts_with($realFilePath, $realDiskRoot)) {
       abort(403, __('Unauthorized path traversal access.'));
   }
   ```
4. **فحص نوع MIME الفعلي:** التأكد عبر `mime_content_type` من أن الملف صورة معتمدة (`image/jpeg`, `image/png`, `image/webp`, `image/gif`) قبل تخديمها.
5. **اتساق العمليات والرفع والحذف (Transactional Upload & Consistency):**
   - تم تغليف إنشاء جلسات التطور `storeCheckin` بمعاملة قاعدة بيانات `DB::transaction`.
   - في حال فشل أي عملية أثناء حفظ الجلسة أو السجلات، يتم التراجع في قاعدة البيانات وحذف أي ملفات تم كتابتها على القرص أثناء المحاولة لمنع تراكم الملفات اليتيمة.
   - في الحذف: تم الحفاظ على مراقب حذف النموذج `deleting` لحذف الملف الفيزيائي المقترن عند حذف السجل.

## 5. بيان التعرض المتبقي وخطة الترحيل الآمنة للملفات السابقة
> [!IMPORTANT]
> **تنبيه أمني صريح حول الملفات المخزنة مسبقاً:**
> إن إنشاء مسار تخديم محمي ومصادق لا يجعل الملفات الفيزيائية القديمة الموجودة في المجلد العام `storage/app/public/progress_photos` غير قابلة للوصول إذا علم المهاجم مسارها المباشر أو خمن اسمها العشوائي، لأن خادم الويب (Nginx / Apache / Laragon) يقوم بتخديم الملفات الثابتة عبر الرابط الرمزي المباشر دون المرور على كود Laravel نهائياً.

وفقاً للشرط الإرشادي الصارم بعدم نقل أو حذف أو نسخ ملفات المستخدمين الحالية بشكل جماعي في هذه المهمة تجنباً لأي انقطاع أو فقدان للبيانات، نورد هنا **خطة ترحيل تشغيلية مستقلة (Migration Plan)** يتم تنفيذها في نافذة صيانة منفصلة:

### خطة الترحيل المقترحة (غير منفذة في هذا التكليف):
1. **تحديث قرص التخزين:** إنشاء قرص تخزين مخصص غير عام في `config/filesystems.php`:
   ```php
   'private' => [
       'driver' => 'local',
       'root'   => storage_path('app/private_progress_photos'),
   ],
   ```
2. **أمر تشغيلي لترحيل الملفات وتحديث السجلات (Artisan Command):**
   - كتابة أمر `php artisan photos:migrate-to-private`.
   - يقوم الأمر بنسخ الملفات الفيزيائية من `storage/app/public/progress_photos` إلى `storage/app/private_progress_photos`.
   - التحقق من وجود الملف في الوجهة الجديدة وتطابق حجمه.
   - حذف الملف من المجلد العام بعد التأكد من النقل الناجح.
3. **حظر الوصول المباشر عبر خادم الويب (Web Server Rule):**
   - إضافة قاعدة في إعدادات Nginx / Apache لحظر أي طلب مباشر على `/storage/progress_photos/*` وإرجاع `403 Forbidden`، وتوجيه كل الطلبات حصرياً إلى مسار التطبيق المحمي.

## 6. التحقيق في مسار التفعيل الإداري ومعالجته (SettingController::updateActivateSection)

### أ. التحقيق في المشكلة
* **الوضع السابق:** السطر 43 في `SettingController.php` كان يحتوي على:
  ```php
  public function updateActivateSection($id, Request $request)
  {
      dd($id, $request);
  }
  ```
* **سياق الاستدعاء:**
  - يتم استدعاؤه عبر طلب AJAX `POST` من واجهة إدارة أقسام الموقع `resources/views/system/activate-section/index.blade.php`.
  - تقوم الدالة في JavaScript بإرسال `id` القسم في مسار الـ URL، وتمرر في جسم الطلب `name` و `value` (حيث القيمة إما `"active"` أو `"inactive"`).
  - يتم التحقق من حالة التفعيل في واجهات الموقع عبر المساعد `active_section($name)`.

### ب. السلوك البرمجي المنفذ
1. **إزالة أمر التنقيح `dd()` نهائياً.**
2. **التحقق من الصلاحيات الإدارية الخادمية:** فحص صلاحية `userCan('system.activate.update')` (المقترنة بمجموعة صلاحيات `view-activate-sections`). رفض أي طلب غير مصرح به أو قادم من حسابات المتدربين.
3. **التحقق الصارم من المدخلات:**
   - فحص معرف القسم `$sectionKey` للتأكد من أنه نصي ولا يحتوي على رموز خبيثة (`regex:/^[a-zA-Z0-9_\-]+$/`).
   - معايرة القيمة المدخلة `$request->input('value')` وقبول القيم المنطقية المعيارية (`active`, `inactive`, `1`, `0`, `true`, `false`) وتحويلها إلى قيمة التعداد `active` أو `inactive`.
4. **التحديث داخل معاملة ذرية (`DB::transaction`):**
   - البحث عن سجل القسم في جدول `activate_section` بالمعرف الرقمي أو بالاسم.
   - إذا وُجد السجل يتم تحديث قيمته.
   - إذا لم يوجد (مثل إضافة قسم جديد في الواجهة لأول مرة)، يتم إنشاؤه تلقائياً برقم معرف تسلسلي سليم.
5. **استجابة متوافقة مع واجهة المستخدم:**
   - إرجاع استجابة JSON معيارية تحتوي على رسالة النجاح وحالة القسم لدعم تنبيهات `toastr` في الواجهة.
   - دعم التوجيه العادي في حال تم إرسال الطلب عبر نموذج ويب تقليدي.
6. **معالجة دالة المساعد `active_section($name)`:**
   - تم تعديل الدالة في `app/Helpers/Global.helpers.php` لتكون آمنة من أخطاء السجلات المفقودة (`Null-safe`) لتعيد `false` دون التسبب في انهيار الصفحة (`500 Error`).
